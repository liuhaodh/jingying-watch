## 过程中修掉的问题

1. **PROPFIND 发不出去**：Android 的 `HttpURLConnection` 只允许标准方法，
   `PROPFIND` 直接抛 `ProtocolException`。改为自己写的 `HttpLite`
   （Socket 直连 HTTP/1.1，支持自定义动词、Basic 鉴权、Range、chunked、
   重定向和自签名 HTTPS）。
2. **PROPFIND 把目录自己当成子项**：有些服务器（含 mock）的 Depth:1 响应
   会带自身 `<response>`，导致「作者目录」里多出自己、作品数虚高。
   在 `DavClient.propfind` 里按 `rel` 过滤掉自身。
3. **进入播放页崩溃**：`window.getInsetsController()` 在 `setContentView`
   之前调用会 NPE；改为 `setContentView` 之后调用，并用
   `decorView.getWindowInsetsController()` + try/catch。
4. **视频画面被过度放大**：`TextureView.setTransform` 的矩阵应基于
   「默认拉满屏幕」再修正宽高比，而不是直接用 `viewWidth/videoWidth`；
   修正后竖屏铺满、横屏完整显示。
5. **拖动翻页不生效**：adb 注入的滑动事件会被合并，`ACTION_UP` 前最后一个
   MOVE 的 offset 不是最终位置；改为在 `ACTION_UP` 用抬手坐标计算最终位移。
6. **上一个视频播完会把正在看的这条顶走**：翻页动画/长按期间不响应
   `onCompleted`，且只接受「当前屏」的完成回调。
7. **图集显示成放大裁切**：图集改用 `FIT_CENTER` 完整显示，并加一层
   0.32 透明度的同图背景，避免大片死黑。
8. **播放失败无法重试**：错误时释放 MediaPlayer，轻点屏幕重新加载详情。

## 第二轮：真实 123pan 片库回归（2026-11-01 下午）

环境：Android 15 模拟器；WebDAV `https://webdav.123pan.cn/webdav`；
真实片库 **16,657 个作品 / 294 位作者**（`净影/Videos/净影`，`净影/作者资料`）。

### 反馈的两个问题

1. **上下滑动不正常**：短促轻扫经常不翻页；偶尔一次滑动跳两条；大库滑动时整个界面卡住（ANR）。
2. **头像显示不正常**：只显示作者名首字，emoji 开头的作者还会出现乱码。

### 定位与修复

- **轻扫被当成点击**：翻页阈值原来要 24% 屏高，且 `VelocityTracker` 在
  adb 注入/事件合并时会算出 0 甚至反方向的速度。
  → 阈值降到 11%，并用「抬手位移 / 手势时长」兜底速度；只有 DOWN/UP 的
  极端情况也按抬手位置补一次翻页。
- **一次滑两条**：上一条刚好播完的自动连播和用户滑动叠加。
  → 翻页动画/拖动中不响应 `onCompleted`；手指 900ms 内动过也不自动跳。
- **ANR / 卡顿**：
  - 16,657 条作品的 `library.json` 约 8MB，原来在主线程解析、并在持有
    索引锁的情况下序列化，主线程会被卡住数秒；
  - 扫描时每收到一位作者就重建整个首页（过滤 1.6 万条 + 重建 295 个
    chips），主线程被反复占满；
  - 播放页每次翻页还会复制两份 1.6 万条的列表。
  → 索引改为后台读取；落盘改成「锁内拷贝快照、锁外序列化」；
    增量结果按 rel 去重并 350ms 合并刷新；chips 1.5s 节流；
    翻页不再复制整份列表，并预取后两条详情。
- **123pan CDN 的 TLS 断流**：媒体 GET 用自写的 Socket TLS 连接时频繁出现
  `DECRYPTION_FAILED_OR_BAD_RECORD_MAC`（PROPFIND 正常）。
  → 媒体 GET/HEAD 改走 Android 系统 `HttpURLConnection`（OkHttp TLS 栈），
    PROPFIND 仍用自写 HttpLite；下载并发降到 2，失败按 0.7s/1.4s/2.1s
    退避重试，播放器错误再自动重连两次。
- **真实头像**：读取 `净影/作者资料/authors.json`（749KB，347 位作者），
  按 抖音号/昵称 匹配 `avatar_local` → `avatar_history` →
  `作者资料/authors/<sec_uid>/` 目录最新图片，下载后本地缓存；
  都找不到才回退首字（`codePointAt`，emoji 不会被截成半个字符）。

### 回归结果

| 场景 | 结果 |
|------|------|
| 首页显示 16,657 作品 / 294 作者，启动 3 秒内可操作 | ✅ |
| 连续 4–6 次 150px 短促轻扫，计数器严格 +1 | ✅ |
| 连续滑过 6 条，无 ANR、无「应用无响应」 | ✅ |
| 真实作者头像（如 @雅儿有点菜.）显示为抖音头像图片 | ✅ |
| 播放大视频、图集、背景音乐 | ✅ |
| 123pan 媒体 TLS 断流日志 | 改用系统 TLS 后为 0 |
| 失败自动重试 / 轻点重试 | ✅ |

> 说明：123pan 的 WebDAV 在本轮测试期间时好时坏（部分时段 PROPFIND 返回
> 404），但 App 侧已用真实片库完成上述回归；mock WebDAV 仍保留用于离线演示。

## 第三轮：本地下载 / 离线观看（2026-11-01 下午）

需求：可以选择把 WebDAV 上的作品下载到手机本地再观看，并且本地文件不能在系统相册里看到。

### 实现

- 新增 `OfflineStore`：把当前作品依赖的 `视频.mp4` / `图片_NN.*` / `音乐.mp3` / `文案.txt`
  逐字节下载到 `Android/data/com.jingying.watch/files/offline/<作品 key>/`，
  写 `meta.json` 记录作品信息；目录和父目录都放 `.nomedia`。
- 播放页右上角新增下载按钮：未下载/下载中百分比/已下载青色对勾；已下载再点可删除。
- 首页封面左上角「已下载」角标，长按封面下载/删除；顶部新增「已下载 N」筛选 chip。
- 设置页新增「本地下载」：数量、占用、私有目录路径、清空按钮，并说明相册不可见。
- 播放时 `FeedPage` 优先读取本地视频/图片/音乐文件，断网也能播放。

### 顺带修掉的问题

- 头像/文案下载时用 HEAD 的 `Content-Length` 判断大小，123pan CDN 的 HEAD 长度比 GET 实际字节小，
  会把头像截成 2×2 / 13×13。现在 `sizeOf` 先用 `GET Range: bytes=0-0` 拿真实总长，
  `MediaProxy` 也会用 GET 返回的总长度修正，`readAll` 按实际文件长度读满。
  修复后缓存头像均为 100×100。

|------|------|
| 播放页下载 1.78MB 视频 | ✅ `offline/<key>/视频.mp4` + `文案.txt` + `meta.json` |
| 关闭 Wi-Fi / 数据后打开「已下载」作品 | ✅ 正常播放，无网络请求 |
| 系统 MediaStore 查询视频/图片 | ✅ 没有 `com.jingying.watch` 的记录 |

| 头像尺寸 | ✅ 修复后为 100×100（原来有 2×2/13×13） |

## 第五轮：背景音乐等画面加载好再响

问题：有些图集作品的背景音乐在封面/第一张图还没出来时就先响了。

### 改动

- `FeedPage` 增加 `visualReady` 和 `musicPrepared` 两个状态，音乐只允许在**画面就绪**后开始：
  - 图集：第一张图真正显示出来（`showAlbumImage` 回调设置 bitmap 后）才算就绪；
  - 视频：`MEDIA_INFO_VIDEO_RENDERING_START` / `hideCover` 首帧渲染后算就绪，并有 1.5s 兜底；
- 所有直接 `musicPlayer.start()` 的地方统一改成 `startMusicIfReady()`：
  - 音乐先准备好 → 等画面；
  - 画面先出来 → 等音乐准备好；
  - 页面切走/暂停/来电/耳机拔出时音乐暂停，回来且画面已就绪才续播；
- 视频播放失败时同时暂停音乐，避免“黑屏但有声音”。

## 第十一轮：下载完成后自动切本地文件（2026-11-01 晚上）

问题：有时候下载已经完成，作品还停在转圈/“视频暂时无法播放”。

### 原因

播放页在下载开始前就用 **WebDAV 代理** 创建了 MediaPlayer。如果这条代理连接失败或一直很慢，
MediaPlayer 会停在 loading/error；下载完成后，页面并不会自动把 player 换成刚下好的本地文件，
所以看起来“下载好了但作品没加载出来”。另外封面缓存可能缓存了网络失败时的占位图。

### 改动

- `FeedPage.onOfflineReady()`：当前作品下载完成时，若处于报错/转圈/未准备/未播放状态，
  释放旧 player，立刻用本地文件重新 `prepareVideo()`，不用退出重进；
- 正在正常播放的作品不会被打断；
- 下载完成/删除时让 `ImageLoader` 清掉这条作品的封面内存 + 磁盘缓存，首页封面会重新从本地视频首帧生成；
- 图集下载完成会重新用本地图片刷新当前页。

### 实测

1. 断网打开一条未下载的视频 → 出现「视频暂时无法播放，轻点重试」；
2. 恢复网络，点右上角下载；
3. 下载完成瞬间日志：

```
offline ready has=true err=0 prepared=false spinner=8
prepare video local=true
```

页面自动清掉错误提示并开始播放本地文件，无需手动重试。

## 第二十一轮：大库性能与索引健壮性（2026-11-03 晚）

目标：不改变交互和界面，只把「1.6 万作品」这条路径上的重复计算、主线程磁盘 IO
和几个会丢回调/吞手势的缺陷处理掉。

### 性能改动

| 位置 | 原来 | 现在 |
|------|------|------|
| `Util.sha1Hex` | 每个字节一次 `String.format("%02x")`，1.6 万作品 ≈ 64 万次格式化 | 十六进制查表 + `MessageDigest` 按线程复用 |
| `Work.parseWorkFolder` | 每个作品新建 `SimpleDateFormat` + 两次正则 `replaceAll` | `ThreadLocal` 格式化器；时间戳按结尾定长判断；去边改手写循环 |
| `Work.sortByIndex` | 比较器里反复跑正则（每次比较 6 次） | 排序前预计算序号，比较时查表 |
| `Work.displayTitle/displayAuthor` | 每次调用都 `trim`、判空 | 首次计算后缓存，文案/详情变更时失效 |
| `Library.filter` | 每次搜索为每条作品拼 5 个字段再 `toLowerCase` | `Work.searchText()` 缓存规范化文本 |
| `Library.stats` | 为了作者数再构造并排序一份作者列表 | 单次遍历 + `HashSet` 去重 |
| `LibraryStore` | `find/indexOf/worksForAuthor` 全是 O(n) 线性扫描；每次读详情都重写 8MB JSON | `rel` / 作者两张哈希索引；落盘加 500ms 去抖，连续 update 合并成一次写 |
| `OfflineStore.has` | 每次调用 2 次文件系统 stat；首页统计对全库调用 ≈ 3 万次磁盘 IO | `load()` 时已逐个校验，之后只查内存索引 |
| `MediaProxy` | 构造时在主线程扫缓存目录；清理任务和下载共用 2 线程池；每 256KB flush | 扫描/清理走独立线程（并跳过 10 分钟内改动的文件）；`streamRange` 只在结束时 flush |
| `ImageLoader` | 占位封面 540×720 ARGB_8888（1.5MB/张） | 360×480 RGB_565（0.34MB/张），和首页格子实际像素匹配 |

### 修掉的缺陷

1. **快速滚动时封面一直空白**：`loadCover/loadImage` 发现同一 key 正在加载时直接 `return`，
   回调永远不会触发。改成 pending 回调列表，一次加载通知所有等待的 view。
2. **头像偶发不显示**：`AvatarStore` 的 `memory` 是普通 `HashMap`，主线程读、下载线程写，
   并发下可能读到脏数据；改成 `ConcurrentHashMap`，并同样补上 pending 回调。
3. **图集左右滑之后第一次点击被吞**：`suppressTapUntilUp` 只在 `ACTION_UP` 里清，滑图集走的是
   提前 `return` 的分支，标记留到下一次点击。改为 `ACTION_DOWN` 复位。
4. **离线索引可能反复全量重扫**：`OfflineStore.load()` 在 `listFiles()` 返回 null（外置存储还没挂载）
   时既不置 `loaded`、也不限流，之后每次 `has()` 都会重新扫一遍目录。改成失败后最多每 3 秒重试一次。
5. **落盘可能互相覆盖**：`saveNow()`（扫描线程）和后台落盘线程会同时写同一个
   `library.json.tmp`，加写锁串行化。
6. **WebDAV 未配置时代理无响应**：`MediaProxy.handle` 里 `client()` 抛
   `IllegalStateException`，被外层 catch 吞掉、连接不返回任何内容；改为直接回 502。

### 验证

纯逻辑部分（目录名解析、文案解析、展示缓存失效、文件分类、筛选/统计、SHA-1/格式化）
用 JDK 17 编译后直接跑断言，60 项全部通过：

```text

```

同一份 1.6 万条数据的新旧写法对照（桌面 JVM，仅用于看相对差异）：

```text
sha1Hex 1.6万次:        旧 529.6 ms → 新  39.7 ms
解析目录名 1.6万次:      旧 356.3 ms → 新 136.3 ms
搜索一次 1.6万条:        旧  44.0 ms → 新  23.0 ms
统计一次 1.6万条:        旧  28.1 ms → 新  17.7 ms
```

构建：`android\build.ps1` 全流程通过，产物 `JingYing-Watch-v1.0.0.apk`（0.14 MB，
minSdk 23 / targetSdk 35，签名与上一版一致）。

- **`DavClient.delete(rel)`**：用自写的 `HttpLite` 发 `DELETE`（带 `Depth: infinity`），
  204/200/202/404 都算成功（404 = 已经没了，幂等）。
- **`DavClient.deleteTree(rel)`**：先按 RFC 4918 一次删掉整个目录；
  服务器不支持递归删目录（403/405/409/501…）时，再 `PROPFIND Depth:1` 出子项逐个删。
  401 直接抛出，不浪费时间重试。
- **`CloudDelete`**：后台线程执行「云端删除 → 本地清理」。
  - 作品：删 `Videos/.../<作品>`，顺带删 `Music/.../<同名作品>`；
  - 作者：删作者目录，顺带删 `Music/<作者>`；
  - 成功后清本地下载（`OfflineStore.delete`）、封面缓存（`ImageLoader.invalidateCover`）、
    播放缓存（`MediaProxy.forget`），并从 `LibraryStore` 索引里移除，不用等下次扫描。
- **入口**：
  - 播放页「评论 → 作品详情」底部红色「删除作品」；
  - 首页长按封面 → 菜单「删除云端作品」；
  - 作者主页右上角「删除作者」。
- **安全措施**：
  - 二次确认弹窗，写明「WebDAV 上的文件会被永久删除 / 本地下载一并清除 / 无法恢复」；
  - `CloudDelete.safe()` 拒绝空路径、片库根目录（`Videos` / `Music`）、没有层级关系的裸名字；
  - `DavClient.delete` 再兜一层：空 rel 直接抛异常，请求都不会发出去；
  - 删除中显示不可取消的「正在删除…」，避免用户以为没反应重复点。
- **UI 同步**：播放页删完自动跳到下一条（`FeedPager.removeCurrent()`），删空就退出；
  首页 `onResume` 发现索引条数变了会重新加载；作者列表 `onResume` 重新读，删掉的作者立即消失。
- **mock WebDAV**：`tools/mock_dav.py` 新增 `do_DELETE`（文件 `os.remove`、目录 `shutil.rmtree`），
  OPTIONS 的 Allow 也加上了 DELETE，方便本地验证。

## 第二十三轮：云端回收站（2026-11-04 下午）

需求：云端做一个回收站文件夹，删除的作品先放进去；App 里加回收站页面，可以恢复或全部彻底删除。

### 云端结构

删除不再直接 `DELETE`，而是把目录 `MOVE` 到片库根下的 `回收站/`：

```text
净影/
  Videos/<作者>/<作品>/            ← 删掉后从这里消失
  Music/<作者>/<作品>/             ← 背景音乐同时移走
  回收站/
    阿星_街拍合集_20261025_160000__20261104_130501/
      data/                        ← 原来的作品/作者目录
      music/                       ← 对应的背景音乐目录
      meta.txt                     ← 原始路径 + 删除时间
```

`meta.txt` 用纯文本，在网盘网页端也能看懂：

```text
type=work
name=阿星_街拍合集_20261025_160000
deleted=1762320000
1.rel=净影/Videos/阿星_94704804628/阿星_街拍合集_20261025_160000
1.music=净影/Music/阿星_94704804628/阿星_街拍合集_20261025_160000
```

作者被删时是 `type=author`，`2.rel` / `2.music` 用来兼容「同一位作者在片库里对应多个目录」的旧路径情况。

### 代码改动

- **`DavClient`** 补齐写操作：`mkcol` / `mkcolPath`（405 视为已存在）、`put`、`move`
  （`Destination` + `Overwrite`）、`exists`（PROPFIND Depth:0，404 → false）。
- **`TrashStore`**：`moveWork` / `moveAuthor` 移入回收站，`list` / `restore` / `deleteItem` / `clearAll`；
  移入成功后才清本地下载、封面缓存、播放缓存和索引；失败会把已经搬进去的目录搬回原位再报错。
- **`TrashMeta`**：meta.txt 的编解码（抽成纯 Java，方便单测）。
- **`TrashActivity`**：回收站页面，单条「恢复」、长按彻底删除、右上角「全部删除」。
- **入口**：首页右上角「回收站」；删除作品/作者的确认框改成「移入回收站」。
- **恢复后的片库**：作品直接按 rel 补一条骨架（不用联网）；作者只重扫这一位（`refreshAuthor`，一次 PROPFIND）。
- **兜底**：服务器不支持 `MOVE`（405/501）时，明确提示「网盘不支持回收站」，让用户选择是否彻底删除。
- **mock WebDAV**：`tools/mock_dav.py` 增加 `MKCOL` / `PUT` / `MOVE`（含 `Destination`、`Overwrite` 处理）。

## 第二十四轮：长按 2× 倍速没效果（2026-11-04 下午）

反馈：长按屏幕，底部出现了「2× 播放中」，但视频还是原速。

### 排查

`FeedPage.applySpeed()` 原来只在 `prepared == true` 时生效，而且有三个漏洞：

1. **加载完成前长按**：`applySpeed` 直接 return，`speedBoost` 虽然记下来了，
   但 `onPrepared` 里 `start()` 之后没有补设置 —— 这一条从打开到播完都不会有倍速；
2. **缓冲 / seek / 切后台回来**会把倍速打回 1×，没有任何补偿；
3. 设置失败时 `catch (Exception ignored)` 把异常吞了，界面上照样显示「2× 播放中」，
   看起来就是“没效果”。

另外 `bind()` / `releasePlayers()` 没有清 `speedBoost`，长按中途被打断时，
下一条视频可能莫名其妙以 2× 开始。

### 改动

- `onPrepared`：如果 `speedBoost` 已置位，**在 `start()` 之前**先设置倍速
  （部分机型只有在 Prepared 状态下设置才真正生效），再 `start()`。
- 新增 `keepSpeed()`：播放中每 220ms 检查一次实际倍速，被打回 1× 就重新设置；
  连续失败超过 3 次就停手，避免刷日志。
- `applySpeed` 改为 `new PlaybackParams().setSpeed(x).setPitch(1f)`，不再复用
  `getPlaybackParams()` 返回的对象；失败时打 `JYWatch` 日志，不再静默。
- 倍速设置失败时，底部提示改成「倍速不可用」，不再谎报「2× 播放中」。
- `bind()` / `releasePlayers()` 复位 `speedBoost` 和失败计数。
- 长按判定从 `work.isVideo()` 放宽到 `!work.isAlbum()`：详情还没读到的作品
  也能先记下倍速，等 `prepare` 完成后再补。

### 说明

本轮无法在真机/模拟器上验证（本机模拟器仍然起不来：`netsim` 拒绝访问 + adb 连不上），
代码层面已经覆盖了上面三条会“看起来没效果”的路径。
如果装机后仍然无效，底部会显示「倍速不可用」（说明这台设备的 `MediaPlayer`
拒绝了 `setPlaybackParams`），可以用 `adb logcat -s JYWatch` 看具体原因。

## 第二十八轮：收藏过的作品再点开按钮还是白的（2026-11-04 傍晚）

## 第二十九轮：拉起抖音后作者主页是空白的（2026-11-04 傍晚）

反馈：点「打开抖音主页」，抖音确实被拉起来了，但停在一个空白主页。

### 根因

抖音的 `snssdk1128://user/profile/<id>` 里，`<id>` 要的是**数字 UID**，

## 第三十轮：拉起抖音作者主页时先跳转到浏览器（2026-11-04 傍晚）

反馈：点了「打开抖音主页」后，手机先打开了浏览器，再由网页二次唤起抖音。

### 根因

上一轮（第二十九轮）把跳转改成了**裸的 https 链接**
`https://www.douyin.com/user/<sec_uid>`，用 `ACTION_VIEW` 交给系统派发。
但抖音的 App Links 在很多手机 / 定制 ROM 上**没有被设为默认链接处理器**，
于是系统把这条 https 链接派发给了浏览器，浏览器再尝试唤起抖音 —— 表现成「先跳浏览器」。

### 修复

核心思路：**显式点名抖音来接这条 Intent，不让浏览器有插手的机会**。

- `DouyinLauncher` 新增 `openIn(url, packageName)`，在 Intent 上 `setPackage("com.ss.android.ugc.aweme")`
  （极速版 `…aweme.lite`），先让抖音自己接这条主页链接；
- 抖音版本太老、没声明该 https 路由导致失败时，再退到数字 UID 的 `snssdk1128://` scheme 试一次（同样点名包名）；
- 仍然接不住才交给系统派发（浏览器 / 应用选择器）→ 按抖音号搜索 → 网页版。
- `AndroidManifest.xml` 里加了 `<queries>` 声明这两个抖音包名，Android 11+ 的包可见性
  才不会拦住 `setPackage` 解析。

### 验证

`android\build.ps1` 全流程通过，产物 `JingYing-Watch-latest.apk`（v1.0.3，versionCode=13，约 0.17 MB）。
aapt2 解包确认 manifest 里已包含 `com.ss.android.ugc.aweme` 的 `<queries>` 声明。

## 第三十一轮：随机观看不是真随机（2026-11-06 中午）

反馈：点「随机观看」，起点是随机的，但往下连看时总是一个作者目录下连续的那一批，
整段顺序并不随机，感觉「不是真随机」。

### 根因

`randomWatch()` 只做了一件事：`new Random().nextInt(pool.size())` 挑一个**起点**，
然后把**按扫描顺序（同一作者目录连续）排好的 pool** 交给 feed 顺序续播。
所以随机起点之后，往下滑永远是那个作者目录里相邻的作品 —— 起点随机，顺序不随机。

### 修复

- 新增纯 Java 工具 `Shuffles.fisherYates(list, random)`：标准 Fisher–Yates 原地打乱，
  不依赖任何 Android API，方便单测。
- `randomWatch()` 把整段 `pool` 打乱后再从 0 开始播放：
  每一次「随机观看」的整段播放顺序都是一次随机排列，不同作者的作品会均匀穿插。
- 保留 `lastRandomKey` 轻保护：万一打乱后第一条正好等于上次的（约万分之一），
  与随机另一个位置交换，避免连续两次第一条一样。
- 不改动 `openFeed` 的签名（另有 3 处调用），只让随机观看从 0 开始播打乱后的列表。

### 验证

`ShufflesTest`（纯 Java，javac -source 8 跑通）4 项全过：
合法排列（去重=1000、排序后与原始一致）、500 次里至少一次重排、
不同种子结果可不同、空列表/单元素不抛异常。

`android\build.ps1` 全流程通过，产物 `JingYing-Watch-latest.apk`（v1.0.4，versionCode=14，约 0.17 MB）。

> 说明：本轮仍无真机回归。装机后点「随机观看」应看到不同作者的作品均匀穿插，
> 而不是总从一个作者的连续视频开始。

## 第三十三轮：性能与健壮性集中优化（2026-11-07 晚）
需求：优化整个项目。做法不是加功能，而是把代码全量审计了一遍（媒体链路、播放页、
封面/下载/收藏、扫描与列表四个方向），挑「用户能感知 + 风险可控」的问题修。

### 数据正确性
- **重新扫描不再丢作品详情**：扫描器只拿得到骨架，`LibraryStore.addBatch()` 以前直接
  覆盖同名作品，于是「某位作者目录里新增一条视频 → 父目录 mtime 变了 → 该作者整批重扫」
  之后，这位作者所有作品的封面/图集类型/文案/音乐全被冲掉。现在骨架会并进已有对象
  （`Work.mergeSkeleton()`），只更新作者/目录名/时间/mtime。
- **扫描裁剪加保护**：以前只要 `all` 非空就 `retain(rels)`，某个作者目录这次读成空的
  （服务端同步中/限流/网络抖动）就会把这位作者的作品从 `library.json` 永久删掉。
  现在只有「每个作者都读成功」的一轮才裁剪；某个以前有作品的作者这次读成空目录时，
  沿用本地缓存并标记失败，本轮不裁剪。
- **占位图不再永久落盘**：封面生成失败时画出来的渐变占位图以前会写进
  `files/covers/<key>.jpg`，下次直接命中，网络恢复后片库也一直停在假封面上。
  现在占位图只放内存；换连接（`App.reloadDav()`）时把「只画了占位图」的 key 忘掉重试。
- **「重新扫描作者资料」真的会联网**：以前 `refresh()` 清空内存映射但没删本地
  `authors.json`，`ensureIndex()` 读到旧文件就跳过联网分支，等于什么都没做。现在先删缓存文件。
- **头像索引不再把主线程卡死**：`ensureIndex()` 以前整段持锁联网（最长 40 秒），
  主线程上的 `cachedSecUid()` 会跟着等 → 点「打开抖音主页」直接 ANR。
  现在联网在锁外，等锁最多 5 秒；失败退避 60 秒；成功/失败都写清状态。
- **本地下载**：`meta.json` 改成「先写 .tmp 再改名」，掉电不会留下半截 JSON
  （旧逻辑启动时会把这种目录整个删掉）；进度分母不再算实况图（`lives` 本来就不下载，
  以前百分比永远到不了 100）；下载途中删除作品会标记取消，收尾时不再把记录写回索引。
- **回收站**：`MOVE` 失败后回滚自己也失败时，不再 `deleteTree`（那会把用户目录真删掉），
  改为报错让人工处理；恢复中途失败会把已经搬回去的部分搬回回收站，避免
  「一半在外面、一半在里面」导致以后永远恢复不了。
- **收藏页**：片库索引还没读完时显示「正在读取本地片库…」并等待，不再误报「还没有收藏」。

### 性能 / 卡顿
- **首页**：搜索改成停手 220ms 再筛；扫描期间冻结作者 chips 和全量统计（结束统一重建一次）；
  用 `LibraryStore.revision()` 判断是否需要重读（以前比数量，删一条补一条就漏刷新）；
  「已下载/下载中」徽标底色改成 `Cell` 构造时建一次，滚动不再每次 `new GradientDrawable`。
- **首页接管进行中的扫描**：扫描是全局的，退出重进/从别的页面起扫描时，新首页以前
  只会 toast「正在扫描」然后永远收不到完成回调；现在挂上去轮询，结束后重读落盘结果。
  停止扫描时也不再展示「只存在于内存、点开 404」的增量。
- **随机观看**：跳过空作品；「只看某作者 / 只看已下载 / 搜索中」时在当前列表里随机。
- **作者列表**：搜索防抖 200ms；同一行滚动回来不再重复请求头像。
- **播放页手势**：去掉「单击暂停要等 260ms 判断双击」的延迟（双击功能早就没接，纯白等）；
  手指按下时给吸附动画收尾（不再在手指下面跳页）；长按和进度条拖动不再打架，
  抬手时先处理 scrub；进度条热区从 46dp 收到 26dp，不再吃掉「背景音乐」那一行；
  静音/下载两个图标的命中区从 ±26dp 收到 ±10dp（原来点下载图标左侧会静音）；
  多指抬起不再可能凭空翻一页。
- **播放页其它**：ticker 每 220ms 只在文字真的变了才 `setText`（避免整棵三屏 relayout），
  退到后台立刻停掉；绑定新作品时取消上一条的封面淡出动画（否则新页面首帧前一片黑）；
  复用页面时 `spinner.stop()`；图集背景音乐先挂 `OnErrorListener` 再 `prepareAsync`，
  失败会释放、下次可重试；静音时不再一直占着音频焦点（以前会把后台播客掐掉）；
  `#话题` 过滤改用带缓存的 `Work.searchText()`。
- **媒体代理**：失败不再粘滞（3 秒退避后允许重新拉，最多连续 5 次），pump 内部重试
  真正生效；`handle()` 里网络探测的 `size` 改为在锁内、只在 `entry.size<=0` 时写入，
  不再把下完的文件改小标成「完整但截断」；本地 socket 请求头改 `BufferedInputStream`；
  每拿到一段数据就 `flush`，几 KB 的小片段不会被 64KB 缓冲攒住；`accept()` 失败加日志和
  200ms 退避（不再 100% CPU 空转）；`clearCache()` 的目录删除移到 maintenance 线程
  （最多 8GB，以前在主线程递归删）；清缓存期间对外报 0。
- **封面/下载索引**：`clearDisk()` 不再在主线程删一万多个文件，并让在途任务别回写；
  `OfflineStore.load()` 不再在 `has()`（列表 bind 里）同步扫目录解析 meta，改成后台建索引
  完成后 `notifyChanged(null)` 刷新。
- **头像**：磁盘解码的 `inSampleSize` 与首次下载统一（以前重启后头像会糊一半）；
  找不到头像的作者记 10 分钟负缓存，不再让唯一一条头像线程反复堵在 404 上。
- **详情只读一次**：同一个作品被「封面生成」「下载」「播放页绑定」同时请求时，以前会各打一次
  PROPFIND；现在 `LibraryScanner.loadDetails()` 把后来的请求挂到同一份结果上。
- **封面磁盘上限**：`files/covers` 以前只增不减（一万多个作品看一遍就是几百 MB），
  现在超过 8000 张按 `lastModified` 清到 6000 张（后台 io 线程做）。
- **下载前检查空间**：`getUsableSpace()` 不够 `1.15 ×` 作品体积时直接报「手机剩余空间不足」，
  不再先下到一半再把 `.part` 删掉重试三次。

## 第三十四轮：云端作品包（tar）按需解包（2026-11-08 下午）
需求：「电脑版」改成每个作品一个 `<作品id>.tar` 后，观看端要能从 WebDAV 直接读这个包，
播放/看图时再解包，而不是只认散目录。

### 实现
- 新增 `TarReader`：自己解析 tar 头（USTAR / PAX 扩展头 / GNU 长文件名，支持中文），
  只依赖 `java.*`，可以直接在桌面 JVM 单测。
- 新增 `DavTarSource`：按 Range 从 WebDAV 的 tar 里读一段/一个成员。列成员只读
  512 字节头并跳过数据块，不下载视频本体；播放时只解「视频.mp4」这一个成员。
- 新增 `ArchiveStore`：成员解到 `files/archive/<包路径哈希>/`，同一个包复用；
  解包缓存 2GB，超过按最后访问清理；离线下载过的作品优先用本地 tar 解包，
  不再走网络。服务器不支持 Range 时退回「整包下到 `files/archive/full` 再解」。
- `RemoteFile` 增加 `archiveRel` + `offset`：包内成员也能走原来的播放/看图链路，
  `inArchive()` 判断要不要先解包；`Work` 增加 `archive`、`archiveSkeleton()`、
  `fromArchive()`、`mergeArchiveDetails()`，并落盘/恢复这些字段。
- 扫描：作者目录下的 `.tar` 文件也当作品（标题先用作品 id，打开后读包内文案补全）；
  详情只读 tar 头和包里的 `文案.txt`，播放时才解视频；图集按需解图片/音乐。
- 播放页：视频/音乐成员异步解包后交给 `MediaPlayer`；图集通过 `ImageLoader` 解包解码；
  视频播成功后用解出来的本机文件生成首帧封面，首页下次绑定就能看到真封面。
- 离线下载：作品包整个下到本地（进度按 tar 体积），播放时从本地 tar 解包。
- 回收站：单个作品的 tar 文件按文件 `MOVE`/恢复；回收站里点 tar 条目可以按 tar 头预览；
  恢复后按 `archiveSkeleton` 加回片库。
- 设置页新增「清空解包缓存（作品包）」，缓存统计里显示解包占用。

### 测试中修掉的三个问题
1. `TrashStore.loadWork` 用 `item.type == "work"` 比较字符串引用，导致 tar 预览永远
   走旧分支、报「回收站里找不到可播放的文件」；改成 `"work".equals(...)`。
2. `TrashActivity.afterRestore` 恢复作品时一律建散目录骨架，tar 作品恢复后打不开；
   改成 `.tar` 用 `Work.archiveSkeleton(...)`。
3. `Work.mergeSkeleton` 会用骨架的 tar mtime 覆盖已经解析出来的发布时间；
   现在「已读详情 + 有文案」时保留文案里的发布时间。

### 验证
- 单元测试：`tools\run-tests.ps1` → **PASS 141 / FAIL 0**（新增 tar 打包/PAX/解包/
  坏包 11 项、tar 作品模型与落盘 16 项）。
- 模拟器（Android 15 x86_64）+ 本地 Java mock WebDAV（Range/PROPFIND/MOVE/DELETE）：
  - 两个 tar 作品被扫描出来（`作品 2 · 作者 1`，角标「作品」）；
  - 视频 tar：详情读出 `周末露营测试作品 / 2026-11-08 10:10 / 8.8 MB`，

## 第三十七轮：修复「作品没点开不显示封面」（2026-11-08 傍晚）
反馈：上一轮的封面自动加载在部分手机上仍然要点开作品才出封面。

### 原因
1. 上一轮视频封面优先走 `MediaDataSource` 取帧；个别机型/服务器不支持或取帧失败，
   只对 ≤20MB 的视频兜底解包，更大的视频就一直停在占位图。
2. 失败生成的占位图被放进了内存 LRU，首页 `peek()` 之后直接命中占位图，
   不再调用 `loadCover()`，所以即使详情/网络已经恢复也不会重试，只有点开作品
   播放成功后才用 `cacheVideoCover()` 换掉。

### 修复
- 视频封面改成「解包优先」：≤80MB 的 `视频.mp4` 直接解到本地再取首帧
  （和播放共用 `files/archive` 缓存，点开时秒开）；>80MB 才先用 MediaDataSource
  按 Range 取帧，失败再退回解包，不再有「20MB 以下才兜底」的限制。
- `ImageLoader` 给失败占位图加 20 秒退避：`peek()` 不再直接返回失败占位图，
  `loadCover()` 在退避结束后清掉内存占位并重新取封面；成功/下载/播放补封面时
  同步清掉失败标记。
- 这样「屏幕可见作品 → 自动读详情 → 解包/取帧 → 真封面」不再依赖点开播放。

### 验证
- 模拟器（Android 15 x86_64）+ 本地 mock WebDAV，一个 7.1MB 视频的 tar：
  设置页清空「封面缓存 + 解包缓存」→ 返回首页等待 → 再进设置页：
  **封面 78.8 KB、解包 7.1 MB**（视频已解出用于取帧），封面不再依赖打开播放。
- `android\build.ps1 -Test`：**PASS 141 / FAIL 0**。
- 产物 `JingYing-Watch-latest.apk`（v1.0.11，versionCode=21）。
- 说明：可见作品越多、视频越大，首屏会解出越多视频；这是「不点开也显示真实封面」
  的代价，缓存仍按 2GB LRU 清理。

## 第三十八轮：封面 / 首页 / 媒体缓存的流畅度优化（2026-11-11 上午）
需求：再做一轮「性能与流畅度」优化，只动用户能感知的主线程卡顿，以及大库、长会话下的
资源占用；不新增功能，不改目录协议。

### 封面：不再为了等详情把线程卡住
- `ImageLoader` 以前在生成 tar/散目录作品的封面时，用 `CountDownLatch.await(25s)` 等详情。
  封面线程池只有 3 条，首页快速滚动遇到几个 tar 作品，后面的格子就要排几十秒。
- 现在需要详情时直接挂在 `LibraryScanner.loadDetails()` 的回调上，任务先返回；
  详情回来后自动重跑这一张封面（`waitingDetails` 去重，详情失败就按失败画占位）。
  封面线程只做解码/取帧，不再被网络等待占住。
- 封面落盘从「先压进 `ByteArrayOutputStream` 再 `toByteArray()`」改成直接压到
  `FileOutputStream`，滚动时少一次几十 KB 的临时数组。

### 首页：作者 chips 和大列表
- 作者列表按 `LibraryStore.revision()` 缓存，搜索时不再每次都 `Library.authors(allWorks)`
  （遍历 + 排序全库）。
- 筛选变化时只改「选中/未选中」两颗 chip 的颜色，不再 `removeAllViews()` 重建整排；
  `ChipTag` 记录状态，只有真的变了才新建 drawable。
- chip 改成**分批挂载**：首屏挂 40 个，横向滚到接近末尾再追加 40 个。
  ListView 的表头每次布局都会重新 measure 所有子 view，作者上千位时这是滚动掉帧的大头。
- 「已下载 N」单独缓存：下载完成只改这一个 chip 的文案，不重建 chips（滚动位置不会跳回最左）。
- 搜索时不再对已排好序的列表重复排序：`Library.filter()` 新增 `sort` 参数，
  首页在 `worksSorted` 时传 `false`；扫描增量追加期间仍会排序。

### 媒体缓存 / 预热
- 预热后面 10 个作品的任务改到单独的 `prefetchPool`（1 条线程），
  播放器拖动进度条后的续传不会再排在 10 个 2MB 预热任务后面干等。
- `cacheBytes()` 结果缓存 15 秒：首页 resume、设置页、统计刷新不再每次递归 stat
  整个缓存目录（最多 8GB）；清缓存 / 删除 / 启动清扫后失效。
- `trimAsync()` 节流 15 秒（改缓存上限时强制立即执行），不会每下完一个文件就扫一遍目录。
- `entries` 超过 3000 条时，把 2 分钟没访问、没有读者、没有在下载的条目从内存摘掉
  （只丢 Entry，不删缓存文件，下次按 `.ok` 直接复用）。

### 头像
- `AvatarStore` 的内存缓存原来是无上限 `ConcurrentHashMap`，片库几千位作者全看过一遍
  就一直占着内存；改成 8MB 的 `LruCache`（按 `getByteCount()` 计），
  失败负缓存也加了 4096 条上限。

### 验证
- `tools\run-tests.ps1`：**PASS 143 / FAIL 0**（新增 2 项：`filter(sort=false)` 保持输入顺序、
  `sort=true` 会给乱序输入排序）。
- `android\build.ps1 -Test` 全流程通过，产物 v1.0.19。
- 桌面 JVM 基准（只为比较相对成本，绝对值不代表手机）：
  - 18 MB / 1.6 万作品的 `library.json`：`new JSONObject(String)` ≈ 420ms，
    流式 `JSONTokener(Reader)` ≈ 610ms → **保留整串解析**，不做流式改造；
  - 完整读库（解析 + `Work.fromJson` × 16000 + 排序）≈ 560ms（JIT 预热后）。

> 说明：本轮没有真机回归（当前环境的 adb 起不来，模拟器连不上）。
> 装机理应看到：① 首页快速滚动时封面不再排队几十秒；② 作者很多时横向 chips
> 滚动更顺、搜索不再卡一下；③ 拖动进度条时后面的 10 个预热不再抢在续传前面；

## 第三十九轮：随机观看图集没有背景音乐（2026-11-11 晚）
反馈：点首页「随机观看」，刷到图集作品时没有背景音乐；从首页点同一个作品进去却有。

### 原因
1. **主因：音乐被「画面就绪」永久卡住。**
   `startMusicIfReady()` 要求 `visualReady`。视频页在 `onPrepared` 里挂了 1.5 秒的
   `visualFallback`，画面出不来也会放行音乐；**图集页从来没挂这个兜底**：
   `visualReady` 只在 `showAlbumImage()` 的回调里、且 `albumIndex == target` 时置位。
   随机观看的候选几乎全是没读过详情的冷数据，一进播放页就要并发做
   「10 个作品预热详情 + 3 屏封面 + 首图解包」，首图很容易超过 3.2 秒轮播间隔；
   轮播一推进 `albumIndex`，先到的那张图回调就被判为过期 → `visualReady` 永远 false
   → 音乐播放器明明 `prepare` 好了也永远不会 `start()`。
   从首页点开时封面/详情多半已经缓存，首图能及时回来，所以听起来「只有随机会坏」。
2. **一次查询失败被永久记成「没有音乐」。** `loadMusicSync()` 无论 PROPFIND 成功还是
   抛异常，最后都写 `work.musicChecked = true`；`app.store.update(work)` 还会落盘。
   随机观看并发高，偶发 404/限流就会把这个作品钉成「无音乐」，之后连重试都没有。
3. **音乐查询排在预热后面。** `loadMusic()` 和 `prefetchAhead()` 的 10 个 `loadDetails`
   共用 `app.details`（3 条线程），当前图集的音乐查询要排队，滑得快就等于没声音。
4. **解包回调串页。** `prepareMusic()`/`prepareVideo()` 里写的是
   `if (work != FeedPage.this.work) return;` —— 两边都是同一个字段，恒为 false。
   页面被复用后，上一条作品的异步解包结果会挂到新作品上（或把新作品的解包状态清掉）。

### 改动
- `FeedPage.prepareAlbum()` 挂 `visualFallback`（1.5 秒）：首图迟迟不来也放行音乐；
  首图回调命中时取消兜底。视频、下载完成后的重载也统一走 `armVisualFallback()`。
- 新增 `ensureMusic()`：一屏只主动查一次独立音乐目录；`prepareMusic()` 里
  「播放器已在跑」不再误把音乐图标藏掉。
- 作品包音乐解包失败 / `MediaPlayer` 报错各给最多 2 次、间隔 1.2 秒的重试；
  `bind()` / `releasePlayers()` 会取消在途重试。
- 解包回调用 `final Work bound = work` 捕获绑定时的作品，杜绝串页。
- `LibraryScanner.loadMusicSync()` 改成返回「是否真的读到目录」：只有成功才置
  `musicChecked`；`loadMusic()` 对失败自动隔 400ms 重试一次。
  另外给旧版本落盘的假 `musicChecked=true` 一次按作品复查机会（`musicRechecked`）。
- `App` 新增单线程 `music` 执行器，`loadMusic()` 不再排在 10 个预热任务后面。
- `MediaPlayer` 先挂到字段再 `prepareAsync()`，异步回调校验 `mediaPlayer == musicPlayer`；
  `setDataSource` 抛异常时也会真正释放刚创建的播放器。

### 验证
- `tools\run-tests.ps1`：**PASS 150 / FAIL 0**（新增 7 项：音乐名/体积/`musicChecked`
  落盘往返，tar 作品合并与往返后音乐仍在包里且 offset/size 不丢）。
- `android\build.ps1 -Test` 全流程通过，产物 v1.0.20。

> 「随机观看」连续刷过几个图集，背景音乐应在 1~2 秒内响起，且不会串到上一条；

## 第四十轮：代码审查后的缺陷修复与工程整理（2026-11-12）

## 第四十三轮：无文案作品不显示抖音作品 ID（2026-11-12）

### 需求
播放作品时，明明没有文案，底部却显示一长串数字（抖音作品 ID）。

### 原因
电脑版把作品打包成 `<作品id>.tar`，`Work.archiveSkeleton()` / `fromJson()` 会把去掉
`.tar` 后的纯数字串写进 `title` / `folderTitle`；而 `Work.captionLine()` 在
`captionText` 为空时 `return value.isEmpty() ? title : value`，于是这串文件名被当成文案
显示。`displayTitle()` 又同样回退到 `title` / `folderTitle`，所以首页卡片、收藏列表、
详情弹层和分享 tar 的文件名也会出现它。散目录作品如果目录名剥完时间戳只剩作者名，
也会被当成文案显示。

### 改动
- `Work.java`：新增 `looksLikeWorkId()`（6~32 位纯数字才算 ID）、`hasCaption()`、
  `usableTitle()`；`captionLine()` 只返回真实文案，没有就返回空串；
  `displayTitle()` 过滤掉 ID 型的 title / folderTitle，最终兜底为 `@作者 的作品`
  （无作者时 `抖音作品`）。**`title` / `folderTitle` 字段本身不动**，
  所以按 ID 搜索、排序、路径定位都不受影响。
- `FeedPage.setCaption()`：空文案把整行 `GONE`（不只是设空文本，避免留下 8dp 空白）；
  详情读完后的刷新统一走 `work.captionLine()`，有文案显示、确实没有保持隐藏。
  `handleCaptionTap()` 本来就检查 `VISIBLE`，隐藏后话题点击不会误触发。
- `FeedActivity.sendTar()`：无文案时不再拼出前导空行，文案与链接都为空就不放
  `EXTRA_TEXT`；`EXTRA_SUBJECT` 仍用 `displayTitle()`，跟着一起不再带 ID。

### 验证
- 新增「空文案不显示作品 ID」26 项：ID 判定边界（6 / 19 位、中文名、带下划线、
  空串 / null）、tar 骨架空文案、落盘往返后仍为空、文案解析后文案与标题都恢复正常、
  纯空白文案、中文目录名不冒充文案但可作标题、有文案时正常显示。

## 第四十四轮：图集作品滑动延迟（2026-11-12）

### 需求
图集作品左右滑切图感觉有延迟、不跟手。

### 排查
只读审查了 `FeedPager`（手势）、`FeedPage.showAlbumImage`（切图）、`ImageLoader`（解码/缓存）、
`MediaProxy.readAll`（取流）全链路，确认**没有在主线程解码 Bitmap**，延迟来自下面几处：

- 图集图片**零预取**：`FeedActivity.prefetchAhead()` 只预热 `work.video`，
  `work.video == null` 的图集直接跳过；划一张才请求一张。
- 缓存未命中时 `showAlbumImage()` 不清 cover、不显示 loading：角标和进度条立刻变，
  画面还是上一张，要等 `MediaProxy.readAll()` 整图下载（最长 45s）+ 全分辨率解码。
- 图集大图和封面**共用 48MB LruCache**：一张 1080×1920 RGB_565 约 4MB，
  翻页封面 / 轮播一挤就被淘汰，来回切反复解码 + 上传 + GC。
- `FeedPager` 要划过 **12% 屏宽**才切图，`ACTION_UP` 的 `albumSwipe` 分支直接 return，
  没有竖直方向那样的抬手速度兜底：短快横扫被完全吞掉。
- 轮播 ticker 固定 3.2s 自续且和手势切图共用 3 条 cover 线程，网络慢时会堆任务。

### 改动
- 新增 `AlbumNav.java`（纯 Java、可单测）：循环索引 `wrap`、相邻预取目标 `neighbors`、
  拖动阈值 `dragCrossed`、抬手快扫兜底 `flingCrossed`。
  `FeedPage` 的轮播 / 上一张 / 下一张统一改走 `wrap`，阈值不再散落内联。
- `ImageLoader.java`：
  - 图集大图分出**独立 `albumMemory`**（min(64MB, maxMemory/4)），不再被封面挤掉；
    `loadImage` / `loadLocalImage` 命中缓存时同步回调，切图当帧换画面。
  - `loadImage` / `loadLocalImage` 合并为可指定线程池的 `runImageTask()`；
    新增 `prefetchImage()` 走**单线程、MIN_PRIORITY 的 `prefetchPool`**，只写缓存不改界面。
  - 预取刻意**不占 `pending`**（用独立 `prefetching` set 去重）：否则用户正好切到
    「正在预取」的那张时，正式请求会挂到低优先级单线程后面排队，比不做预取还慢。
    预取先完成且有正式请求在等就顺手交付；预取失败则不消费等待队列，交给
    高优先级线程自己交付，避免画面永远停在旧图。
  - `clearDisk()` 一并清 `albumMemory` 与 `prefetching`。
- `FeedPage.java`：每次 `showAlbumImage()` 后对当前屏预取前后相邻图
  （`AlbumNav.neighbors`，两张图只预取一次、单张不预取），按离线本地 / WebDAV 分流。
- `FeedPager.java`：切图阈值 12% → **8%**（`AlbumNav.dragCrossed`），
  `ACTION_UP` 的 `albumSwipe` 分支按抬手位移 + 速度补切一张
  （`flingCrossed`，位移 > 5% 屏宽且 > 300px/s）；一次手势仍只切一张。

### 验证
- 新增「图集切图与预取」23 项：循环索引正负数 / 空图集 / 越界回绕，
  相邻预取目标（3 张 / 2 张 / 1 张 / 空 / 末位回绕），8% 拖动阈值，
  快扫 / 慢推 / 位移不足 / 时长为 0。单元测试 **PASS 224 / FAIL 0**（原 201）。
- `android\build.ps1 -NoBump -Test` 两轮均全绿（含修正预取调度前后）：

- 最终 `android\build.ps1 -Test` 同样全绿，版本号按脚本惯例自增到
  **v1.0.24（code 34）**，产物 `android/JingYing-Watch-v1.0.24.apk`。
