## 过程中修掉的问题

1. **PROPFIND 发不出去**：Android 的 `HttpURLConnection` 只允许标准方法，
   `PROPFIND` 直接抛 `ProtocolException`。改为自己写的 `HttpLite`
   （Socket 直连 HTTP/1.1，支持自定义动词、Basic 鉴权、Range、chunked、
   重定向和自签名 HTTPS）。
2. **PROPFIND 把目录自己当成子项**：有些服务器（含 mock）的 Depth:1 响应
   会带自身 `<response>`，导致「作者目录」里多出自己、作品数虚高。
   在 `DavClient.propfind` 里按 `rel` 过滤掉自身。
3. **进入播放页崩溃**：`window.getInsetsController()` 在 `setContentView`
   之前调用会 NPE；改为 `setContentView` 之后调用，并用
   `decorView.getWindowInsetsController()` + try/catch。
4. **视频画面被过度放大**：`TextureView.setTransform` 的矩阵应基于
   「默认拉满屏幕」再修正宽高比，而不是直接用 `viewWidth/videoWidth`；
   修正后竖屏铺满、横屏完整显示。
5. **拖动翻页不生效**：adb 注入的滑动事件会被合并，`ACTION_UP` 前最后一个
   MOVE 的 offset 不是最终位置；改为在 `ACTION_UP` 用抬手坐标计算最终位移。
6. **上一个视频播完会把正在看的这条顶走**：翻页动画/长按期间不响应
   `onCompleted`，且只接受「当前屏」的完成回调。
7. **图集显示成放大裁切**：图集改用 `FIT_CENTER` 完整显示，并加一层
   0.32 透明度的同图背景，避免大片死黑。
8. **播放失败无法重试**：错误时释放 MediaPlayer，轻点屏幕重新加载详情。

## 第二轮：真实 123pan 片库回归（2026-11-01 下午）

环境：Android 15 模拟器；WebDAV `https://webdav.123pan.cn/webdav`；
真实片库 **16,657 个作品 / 294 位作者**（`净影/Videos/净影`，`净影/作者资料`）。

### 反馈的两个问题

1. **上下滑动不正常**：短促轻扫经常不翻页；偶尔一次滑动跳两条；大库滑动时整个界面卡住（ANR）。
2. **头像显示不正常**：只显示作者名首字，emoji 开头的作者还会出现乱码。

### 定位与修复

- **轻扫被当成点击**：翻页阈值原来要 24% 屏高，且 `VelocityTracker` 在
  adb 注入/事件合并时会算出 0 甚至反方向的速度。
  → 阈值降到 11%，并用「抬手位移 / 手势时长」兜底速度；只有 DOWN/UP 的
  极端情况也按抬手位置补一次翻页。
- **一次滑两条**：上一条刚好播完的自动连播和用户滑动叠加。
  → 翻页动画/拖动中不响应 `onCompleted`；手指 900ms 内动过也不自动跳。
- **ANR / 卡顿**：
  - 16,657 条作品的 `library.json` 约 8MB，原来在主线程解析、并在持有
    索引锁的情况下序列化，主线程会被卡住数秒；
  - 扫描时每收到一位作者就重建整个首页（过滤 1.6 万条 + 重建 295 个
    chips），主线程被反复占满；
  - 播放页每次翻页还会复制两份 1.6 万条的列表。
  → 索引改为后台读取；落盘改成「锁内拷贝快照、锁外序列化」；
    增量结果按 rel 去重并 350ms 合并刷新；chips 1.5s 节流；
    翻页不再复制整份列表，并预取后两条详情。
- **123pan CDN 的 TLS 断流**：媒体 GET 用自写的 Socket TLS 连接时频繁出现
  `DECRYPTION_FAILED_OR_BAD_RECORD_MAC`（PROPFIND 正常）。
  → 媒体 GET/HEAD 改走 Android 系统 `HttpURLConnection`（OkHttp TLS 栈），
    PROPFIND 仍用自写 HttpLite；下载并发降到 2，失败按 0.7s/1.4s/2.1s
    退避重试，播放器错误再自动重连两次。
- **真实头像**：读取 `净影/作者资料/authors.json`（749KB，347 位作者），
  按 抖音号/昵称 匹配 `avatar_local` → `avatar_history` →
  `作者资料/authors/<sec_uid>/` 目录最新图片，下载后本地缓存；
  都找不到才回退首字（`codePointAt`，emoji 不会被截成半个字符）。

### 回归结果

| 场景 | 结果 |
|------|------|
| 首页显示 16,657 作品 / 294 作者，启动 3 秒内可操作 | ✅ |
| 连续 4–6 次 150px 短促轻扫，计数器严格 +1 | ✅ |
| 连续滑过 6 条，无 ANR、无「应用无响应」 | ✅ |
| 真实作者头像（如 @雅儿有点菜.）显示为抖音头像图片 | ✅ |
| 播放大视频、图集、背景音乐 | ✅ |
| 123pan 媒体 TLS 断流日志 | 改用系统 TLS 后为 0 |
| 失败自动重试 / 轻点重试 | ✅ |

> 说明：123pan 的 WebDAV 在本轮测试期间时好时坏（部分时段 PROPFIND 返回
> 404），但 App 侧已用真实片库完成上述回归；mock WebDAV 仍保留用于离线演示。

## 第三轮：本地下载 / 离线观看（2026-11-01 下午）

需求：可以选择把 WebDAV 上的作品下载到手机本地再观看，并且本地文件不能在系统相册里看到。

### 实现

- 新增 `OfflineStore`：把当前作品依赖的 `视频.mp4` / `图片_NN.*` / `音乐.mp3` / `文案.txt`
  逐字节下载到 `Android/data/com.jingying.watch/files/offline/<作品 key>/`，
  写 `meta.json` 记录作品信息；目录和父目录都放 `.nomedia`。
- 播放页右上角新增下载按钮：未下载/下载中百分比/已下载青色对勾；已下载再点可删除。
- 首页封面左上角「已下载」角标，长按封面下载/删除；顶部新增「已下载 N」筛选 chip。
- 设置页新增「本地下载」：数量、占用、私有目录路径、清空按钮，并说明相册不可见。
- 播放时 `FeedPage` 优先读取本地视频/图片/音乐文件，断网也能播放。

### 顺带修掉的问题

- 头像/文案下载时用 HEAD 的 `Content-Length` 判断大小，123pan CDN 的 HEAD 长度比 GET 实际字节小，
  会把头像截成 2×2 / 13×13。现在 `sizeOf` 先用 `GET Range: bytes=0-0` 拿真实总长，
  `MediaProxy` 也会用 GET 返回的总长度修正，`readAll` 按实际文件长度读满。
  修复后缓存头像均为 100×100。

|------|------|
| 播放页下载 1.78MB 视频 | ✅ `offline/<key>/视频.mp4` + `文案.txt` + `meta.json` |
| 关闭 Wi-Fi / 数据后打开「已下载」作品 | ✅ 正常播放，无网络请求 |
| 系统 MediaStore 查询视频/图片 | ✅ 没有 `com.jingying.watch` 的记录 |

| 头像尺寸 | ✅ 修复后为 100×100（原来有 2×2/13×13） |

## 第五轮：背景音乐等画面加载好再响

问题：有些图集作品的背景音乐在封面/第一张图还没出来时就先响了。

### 改动

- `FeedPage` 增加 `visualReady` 和 `musicPrepared` 两个状态，音乐只允许在**画面就绪**后开始：
  - 图集：第一张图真正显示出来（`showAlbumImage` 回调设置 bitmap 后）才算就绪；
  - 视频：`MEDIA_INFO_VIDEO_RENDERING_START` / `hideCover` 首帧渲染后算就绪，并有 1.5s 兜底；
- 所有直接 `musicPlayer.start()` 的地方统一改成 `startMusicIfReady()`：
  - 音乐先准备好 → 等画面；
  - 画面先出来 → 等音乐准备好；
  - 页面切走/暂停/来电/耳机拔出时音乐暂停，回来且画面已就绪才续播；
- 视频播放失败时同时暂停音乐，避免“黑屏但有声音”。

## 第十一轮：下载完成后自动切本地文件（2026-11-01 晚上）

问题：有时候下载已经完成，作品还停在转圈/“视频暂时无法播放”。

### 原因

播放页在下载开始前就用 **WebDAV 代理** 创建了 MediaPlayer。如果这条代理连接失败或一直很慢，
MediaPlayer 会停在 loading/error；下载完成后，页面并不会自动把 player 换成刚下好的本地文件，
所以看起来“下载好了但作品没加载出来”。另外封面缓存可能缓存了网络失败时的占位图。

### 改动

- `FeedPage.onOfflineReady()`：当前作品下载完成时，若处于报错/转圈/未准备/未播放状态，
  释放旧 player，立刻用本地文件重新 `prepareVideo()`，不用退出重进；
- 正在正常播放的作品不会被打断；
- 下载完成/删除时让 `ImageLoader` 清掉这条作品的封面内存 + 磁盘缓存，首页封面会重新从本地视频首帧生成；
- 图集下载完成会重新用本地图片刷新当前页。

### 实测

1. 断网打开一条未下载的视频 → 出现「视频暂时无法播放，轻点重试」；
2. 恢复网络，点右上角下载；
3. 下载完成瞬间日志：

```
offline ready has=true err=0 prepared=false spinner=8
prepare video local=true
```

页面自动清掉错误提示并开始播放本地文件，无需手动重试。

## 第二十一轮：大库性能与索引健壮性（2026-11-03 晚）

目标：不改变交互和界面，只把「1.6 万作品」这条路径上的重复计算、主线程磁盘 IO
和几个会丢回调/吞手势的缺陷处理掉。

### 性能改动

| 位置 | 原来 | 现在 |
|------|------|------|
| `Util.sha1Hex` | 每个字节一次 `String.format("%02x")`，1.6 万作品 ≈ 64 万次格式化 | 十六进制查表 + `MessageDigest` 按线程复用 |
| `Work.parseWorkFolder` | 每个作品新建 `SimpleDateFormat` + 两次正则 `replaceAll` | `ThreadLocal` 格式化器；时间戳按结尾定长判断；去边改手写循环 |
| `Work.sortByIndex` | 比较器里反复跑正则（每次比较 6 次） | 排序前预计算序号，比较时查表 |
| `Work.displayTitle/displayAuthor` | 每次调用都 `trim`、判空 | 首次计算后缓存，文案/详情变更时失效 |
| `Library.filter` | 每次搜索为每条作品拼 5 个字段再 `toLowerCase` | `Work.searchText()` 缓存规范化文本 |
| `Library.stats` | 为了作者数再构造并排序一份作者列表 | 单次遍历 + `HashSet` 去重 |
| `LibraryStore` | `find/indexOf/worksForAuthor` 全是 O(n) 线性扫描；每次读详情都重写 8MB JSON | `rel` / 作者两张哈希索引；落盘加 500ms 去抖，连续 update 合并成一次写 |
| `OfflineStore.has` | 每次调用 2 次文件系统 stat；首页统计对全库调用 ≈ 3 万次磁盘 IO | `load()` 时已逐个校验，之后只查内存索引 |
| `MediaProxy` | 构造时在主线程扫缓存目录；清理任务和下载共用 2 线程池；每 256KB flush | 扫描/清理走独立线程（并跳过 10 分钟内改动的文件）；`streamRange` 只在结束时 flush |
| `ImageLoader` | 占位封面 540×720 ARGB_8888（1.5MB/张） | 360×480 RGB_565（0.34MB/张），和首页格子实际像素匹配 |

### 修掉的缺陷

1. **快速滚动时封面一直空白**：`loadCover/loadImage` 发现同一 key 正在加载时直接 `return`，
   回调永远不会触发。改成 pending 回调列表，一次加载通知所有等待的 view。
2. **头像偶发不显示**：`AvatarStore` 的 `memory` 是普通 `HashMap`，主线程读、下载线程写，
   并发下可能读到脏数据；改成 `ConcurrentHashMap`，并同样补上 pending 回调。
3. **图集左右滑之后第一次点击被吞**：`suppressTapUntilUp` 只在 `ACTION_UP` 里清，滑图集走的是
   提前 `return` 的分支，标记留到下一次点击。改为 `ACTION_DOWN` 复位。
4. **离线索引可能反复全量重扫**：`OfflineStore.load()` 在 `listFiles()` 返回 null（外置存储还没挂载）
   时既不置 `loaded`、也不限流，之后每次 `has()` 都会重新扫一遍目录。改成失败后最多每 3 秒重试一次。
5. **落盘可能互相覆盖**：`saveNow()`（扫描线程）和后台落盘线程会同时写同一个
   `library.json.tmp`，加写锁串行化。
6. **WebDAV 未配置时代理无响应**：`MediaProxy.handle` 里 `client()` 抛
   `IllegalStateException`，被外层 catch 吞掉、连接不返回任何内容；改为直接回 502。

### 验证

纯逻辑部分（目录名解析、文案解析、展示缓存失效、文件分类、筛选/统计、SHA-1/格式化）
用 JDK 17 编译后直接跑断言，60 项全部通过：

```text

```

同一份 1.6 万条数据的新旧写法对照（桌面 JVM，仅用于看相对差异）：

```text
sha1Hex 1.6万次:        旧 529.6 ms → 新  39.7 ms
解析目录名 1.6万次:      旧 356.3 ms → 新 136.3 ms
搜索一次 1.6万条:        旧  44.0 ms → 新  23.0 ms
统计一次 1.6万条:        旧  28.1 ms → 新  17.7 ms
```

构建：`android\build.ps1` 全流程通过，产物 `JingYing-Watch-v1.0.0.apk`（0.14 MB，
minSdk 23 / targetSdk 35，签名与上一版一致）。

- **`DavClient.delete(rel)`**：用自写的 `HttpLite` 发 `DELETE`（带 `Depth: infinity`），
  204/200/202/404 都算成功（404 = 已经没了，幂等）。
- **`DavClient.deleteTree(rel)`**：先按 RFC 4918 一次删掉整个目录；
  服务器不支持递归删目录（403/405/409/501…）时，再 `PROPFIND Depth:1` 出子项逐个删。
  401 直接抛出，不浪费时间重试。
- **`CloudDelete`**：后台线程执行「云端删除 → 本地清理」。
  - 作品：删 `Videos/.../<作品>`，顺带删 `Music/.../<同名作品>`；
  - 作者：删作者目录，顺带删 `Music/<作者>`；
  - 成功后清本地下载（`OfflineStore.delete`）、封面缓存（`ImageLoader.invalidateCover`）、
    播放缓存（`MediaProxy.forget`），并从 `LibraryStore` 索引里移除，不用等下次扫描。
- **入口**：
  - 播放页「评论 → 作品详情」底部红色「删除作品」；
  - 首页长按封面 → 菜单「删除云端作品」；
  - 作者主页右上角「删除作者」。
- **安全措施**：
  - 二次确认弹窗，写明「WebDAV 上的文件会被永久删除 / 本地下载一并清除 / 无法恢复」；
  - `CloudDelete.safe()` 拒绝空路径、片库根目录（`Videos` / `Music`）、没有层级关系的裸名字；
  - `DavClient.delete` 再兜一层：空 rel 直接抛异常，请求都不会发出去；
  - 删除中显示不可取消的「正在删除…」，避免用户以为没反应重复点。
- **UI 同步**：播放页删完自动跳到下一条（`FeedPager.removeCurrent()`），删空就退出；
  首页 `onResume` 发现索引条数变了会重新加载；作者列表 `onResume` 重新读，删掉的作者立即消失。
- **mock WebDAV**：`tools/mock_dav.py` 新增 `do_DELETE`（文件 `os.remove`、目录 `shutil.rmtree`），
  OPTIONS 的 Allow 也加上了 DELETE，方便本地验证。

## 第二十三轮：云端回收站（2026-11-04 下午）

需求：云端做一个回收站文件夹，删除的作品先放进去；App 里加回收站页面，可以恢复或全部彻底删除。

### 云端结构

删除不再直接 `DELETE`，而是把目录 `MOVE` 到片库根下的 `回收站/`：

```text
净影/
  Videos/<作者>/<作品>/            ← 删掉后从这里消失
  Music/<作者>/<作品>/             ← 背景音乐同时移走
  回收站/
    阿星_街拍合集_20261025_160000__20261104_130501/
      data/                        ← 原来的作品/作者目录
      music/                       ← 对应的背景音乐目录
      meta.txt                     ← 原始路径 + 删除时间
```

`meta.txt` 用纯文本，在网盘网页端也能看懂：

```text
type=work
name=阿星_街拍合集_20261025_160000
deleted=1762320000
1.rel=净影/Videos/阿星_94704804628/阿星_街拍合集_20261025_160000
1.music=净影/Music/阿星_94704804628/阿星_街拍合集_20261025_160000
```

作者被删时是 `type=author`，`2.rel` / `2.music` 用来兼容「同一位作者在片库里对应多个目录」的旧路径情况。

### 代码改动

- **`DavClient`** 补齐写操作：`mkcol` / `mkcolPath`（405 视为已存在）、`put`、`move`
  （`Destination` + `Overwrite`）、`exists`（PROPFIND Depth:0，404 → false）。
- **`TrashStore`**：`moveWork` / `moveAuthor` 移入回收站，`list` / `restore` / `deleteItem` / `clearAll`；
  移入成功后才清本地下载、封面缓存、播放缓存和索引；失败会把已经搬进去的目录搬回原位再报错。
- **`TrashMeta`**：meta.txt 的编解码（抽成纯 Java，方便单测）。
- **`TrashActivity`**：回收站页面，单条「恢复」、长按彻底删除、右上角「全部删除」。
- **入口**：首页右上角「回收站」；删除作品/作者的确认框改成「移入回收站」。
- **恢复后的片库**：作品直接按 rel 补一条骨架（不用联网）；作者只重扫这一位（`refreshAuthor`，一次 PROPFIND）。
- **兜底**：服务器不支持 `MOVE`（405/501）时，明确提示「网盘不支持回收站」，让用户选择是否彻底删除。
- **mock WebDAV**：`tools/mock_dav.py` 增加 `MKCOL` / `PUT` / `MOVE`（含 `Destination`、`Overwrite` 处理）。

## 第二十四轮：长按 2× 倍速没效果（2026-11-04 下午）

反馈：长按屏幕，底部出现了「2× 播放中」，但视频还是原速。

### 排查

`FeedPage.applySpeed()` 原来只在 `prepared == true` 时生效，而且有三个漏洞：

1. **加载完成前长按**：`applySpeed` 直接 return，`speedBoost` 虽然记下来了，
   但 `onPrepared` 里 `start()` 之后没有补设置 —— 这一条从打开到播完都不会有倍速；
2. **缓冲 / seek / 切后台回来**会把倍速打回 1×，没有任何补偿；
3. 设置失败时 `catch (Exception ignored)` 把异常吞了，界面上照样显示「2× 播放中」，
   看起来就是“没效果”。

另外 `bind()` / `releasePlayers()` 没有清 `speedBoost`，长按中途被打断时，
下一条视频可能莫名其妙以 2× 开始。

### 改动

- `onPrepared`：如果 `speedBoost` 已置位，**在 `start()` 之前**先设置倍速
  （部分机型只有在 Prepared 状态下设置才真正生效），再 `start()`。
- 新增 `keepSpeed()`：播放中每 220ms 检查一次实际倍速，被打回 1× 就重新设置；
  连续失败超过 3 次就停手，避免刷日志。
- `applySpeed` 改为 `new PlaybackParams().setSpeed(x).setPitch(1f)`，不再复用
  `getPlaybackParams()` 返回的对象；失败时打 `JYWatch` 日志，不再静默。
- 倍速设置失败时，底部提示改成「倍速不可用」，不再谎报「2× 播放中」。
- `bind()` / `releasePlayers()` 复位 `speedBoost` 和失败计数。
- 长按判定从 `work.isVideo()` 放宽到 `!work.isAlbum()`：详情还没读到的作品
  也能先记下倍速，等 `prepare` 完成后再补。

### 说明

本轮无法在真机/模拟器上验证（本机模拟器仍然起不来：`netsim` 拒绝访问 + adb 连不上），
代码层面已经覆盖了上面三条会“看起来没效果”的路径。
如果装机后仍然无效，底部会显示「倍速不可用」（说明这台设备的 `MediaPlayer`
拒绝了 `setPlaybackParams`），可以用 `adb logcat -s JYWatch` 看具体原因。

## 第二十八轮：收藏过的作品再点开按钮还是白的（2026-11-04 傍晚）

## 第二十九轮：拉起抖音后作者主页是空白的（2026-11-04 傍晚）

反馈：点「打开抖音主页」，抖音确实被拉起来了，但停在一个空白主页。

### 根因

抖音的 `snssdk1128://user/profile/<id>` 里，`<id>` 要的是**数字 UID**，

## 第三十轮：拉起抖音作者主页时先跳转到浏览器（2026-11-04 傍晚）

反馈：点了「打开抖音主页」后，手机先打开了浏览器，再由网页二次唤起抖音。

### 根因

上一轮（第二十九轮）把跳转改成了**裸的 https 链接**
`https://www.douyin.com/user/<sec_uid>`，用 `ACTION_VIEW` 交给系统派发。
但抖音的 App Links 在很多手机 / 定制 ROM 上**没有被设为默认链接处理器**，
于是系统把这条 https 链接派发给了浏览器，浏览器再尝试唤起抖音 —— 表现成「先跳浏览器」。

### 修复

核心思路：**显式点名抖音来接这条 Intent，不让浏览器有插手的机会**。

- `DouyinLauncher` 新增 `openIn(url, packageName)`，在 Intent 上 `setPackage("com.ss.android.ugc.aweme")`
  （极速版 `…aweme.lite`），先让抖音自己接这条主页链接；
- 抖音版本太老、没声明该 https 路由导致失败时，再退到数字 UID 的 `snssdk1128://` scheme 试一次（同样点名包名）；
- 仍然接不住才交给系统派发（浏览器 / 应用选择器）→ 按抖音号搜索 → 网页版。
- `AndroidManifest.xml` 里加了 `<queries>` 声明这两个抖音包名，Android 11+ 的包可见性
  才不会拦住 `setPackage` 解析。

### 验证

`android\build.ps1` 全流程通过，产物 `JingYing-Watch-latest.apk`（v1.0.3，versionCode=13，约 0.17 MB）。
aapt2 解包确认 manifest 里已包含 `com.ss.android.ugc.aweme` 的 `<queries>` 声明。

> 说明：本轮仍无真机回归。装机后：
> ① 点「打开抖音主页」应**直接进抖音作者主页**，不再经过浏览器；
> ② 若个别 ROM 仍弹「用浏览器打开 / 用抖音打开」的选择器，选「抖音」并勾「始终」即可；
> ③ 演示片库的 `sec_uid` 是假值，进主页必然是空白页，属预期，要用真实片库。

## 第三十一轮：随机观看不是真随机（2026-11-06 中午）

反馈：点「随机观看」，起点是随机的，但往下连看时总是一个作者目录下连续的那一批，
整段顺序并不随机，感觉「不是真随机」。

### 根因

`randomWatch()` 只做了一件事：`new Random().nextInt(pool.size())` 挑一个**起点**，
然后把**按扫描顺序（同一作者目录连续）排好的 pool** 交给 feed 顺序续播。
所以随机起点之后，往下滑永远是那个作者目录里相邻的作品 —— 起点随机，顺序不随机。

### 修复

- 新增纯 Java 工具 `Shuffles.fisherYates(list, random)`：标准 Fisher–Yates 原地打乱，
  不依赖任何 Android API，方便单测。
- `randomWatch()` 把整段 `pool` 打乱后再从 0 开始播放：
  每一次「随机观看」的整段播放顺序都是一次随机排列，不同作者的作品会均匀穿插。
- 保留 `lastRandomKey` 轻保护：万一打乱后第一条正好等于上次的（约万分之一），
  与随机另一个位置交换，避免连续两次第一条一样。
- 不改动 `openFeed` 的签名（另有 3 处调用），只让随机观看从 0 开始播打乱后的列表。

### 验证

`ShufflesTest`（纯 Java，javac -source 8 跑通）4 项全过：
合法排列（去重=1000、排序后与原始一致）、500 次里至少一次重排、
不同种子结果可不同、空列表/单元素不抛异常。

`android\build.ps1` 全流程通过，产物 `JingYing-Watch-latest.apk`（v1.0.4，versionCode=14，约 0.17 MB）。

> 说明：本轮仍无真机回归。装机后点「随机观看」应看到不同作者的作品均匀穿插，
> 而不是总从一个作者的连续视频开始。

## 第三十二轮：播放页发布时间后面显示作品总大小（2026-11-06 中午）

需求：播放作品时，在发布时间后面加上这个作品所有文件加起来的大小。

```text
发布时间 2026-01-02 13:45 · 24.6 MB
```

  `onDetailsReady()` 本身会再调一次 `updatePublishTime()`，详情（含图集音乐）读完后大小自动补上。
- 没有发布时间但有大小（极少数目录名解析不出时间）时，只显示大小，不再整行隐藏。
